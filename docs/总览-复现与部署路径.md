## 一、项目目标

目标不是“单独跨链”，而是完整业务闭环：

1. 源链把 `tokenIn` 换成 `OFT`
2. 通过 LayerZero 跨链
3. 目标链收到 `OFT`
4. 目标链把 `OFT` 卖成 `payoutToken`
5. 链下 watcher 监控到账并自动触发卖出

抽象流程：

```text
源链:
tokenIn -> swap -> OFT -> bridge

目标链:
收到 OFT -> swap -> payoutToken

链下:
监控到账 -> 自动卖出
```

## 二、当前实现结构

### 1. 链上主流程

核心合约：
- `src/examples/UnifiedOFTWorkflow.sol`

职责：
- 源链：`swapAndBridge(...)`
- 目标链：`swapReceivedOFT(...)`

这份合约已经支持：
- caller whitelist
- swap adapter whitelist
- bridge adapter whitelist
- source route config
- destination route config

### 2. 测试网 OFT

测试网 OFT 合约：
- `src/testnet/TestOFT.sol`

职责：
- 在测试网提供真实可用的 OFT
- 用于 Amoy / Base Sepolia 的跨链测试

### 3. DEX 接入

当前已经有两类 swap adapter：

- `src/adapters/UniswapV2SwapAdapter.sol`
  - Router 风格
- `src/adapters/V2PairSwapAdapter.sol`
  - 直接与 Pair 交互

当前测试里实际使用的是：
- `V2PairSwapAdapter`

原因：
- 对我们自己在测试网部署的最小 UniswapV2 风格池子更稳
- 不依赖 Router 内部对 pair 地址的计算细节

### 4. 链下 watcher

脚本：
- `scripts/testnet/watch-destination-balance-and-sell.js`

职责：
- 扫描目标链 OFT 到账
- 记录到账事件
- 计算卖出预估
- 自动调用 `swapReceivedOFT(...)`
- 写状态文件
- 做失败重试

## 四、主网双 fork 复刻

你给了 3 笔主网交易：

- Polygon 源链：
  - `0x66fdd4c84e47a80db7124979c76591078e57dbf984958d64f7b60147ae3d3db8`
- Base 到账：
  - `0xdccbd94bd8dc9c875108e6b30dbd9842c7d8d1ac05bd64a3c4b06e9b854b1d7f`
- Base 卖出：
  - `0xaa38ca9584c265838fd0da4564b01dc3d4ce98e0f54f87d62e76bea26002efb3`

当前已经实现了：

- 通用 fork 回放工具
  - `scripts/fork/replay-utils.js`
- 单笔回放脚本
  - `scripts/fork/replay-tx-on-hardhat-fork.js`
- 三步顺序回放脚本
  - `scripts/fork/replay-three-step-mainnet-flow.js`

对应文档：
- `docs/主网双fork复刻方案.md`

当前结论：
- Base 主网回放可以继续推进
- Polygon 主网回放对 RPC 和 fork 引擎要求更高
- 已经确认不能随便用普通公共 RPC 直接完成历史回放
- 当前更可用的公共候选是：
  - Polygon: `https://polygon.drpc.org`
  - Base: `https://mainnet.base.org`

## 五、为什么要分“测试网验证”和“主网复刻”

因为它们验证的问题不一样。

### 测试网验证

验证的是：
- 合约结构是否成立
- 真跨链是否成立
- 两边 workflow 是否成立
- 真实 DEX 风格池子是否成立
- watcher 是否能工作

### 主网双 fork 复刻

验证的是：
- 真实主网交易行为能不能被重放
- 主网真实池子状态下，路径和结果是否符合预期
- 主网样本行为是不是和我们理解的一致

所以两者不是替代关系，而是互补关系。

## 六、当前已经得到的核心结论

1. 这不是只能做“单独跨链”的系统
2. 当前链上主流程已经足以支撑：
   - 源链 swap + bridge
   - 目标链卖出
3. watcher 也是必须组件，而且已经补上
4. 测试网已经证明“真实 DEX 池子 + 真跨链 + 自动卖出”是可行的
5. 主网双 fork 也已经进入可执行阶段，只是 RPC 条件更苛刻

## 七、如果要往真实部署收敛

后面还要做的工作可以分成几类。

### 1. 工程化

- watcher 去重进一步增强
- watcher 重试策略更细
- watcher 日志落盘更完整
- source tx 与 sell tx 的关联记录更明确

### 2. 配置化

- 将测试网配置与主网配置分层
- 把 route / adapter / token 地址配置整理成最终版本
- 把 `.env` 和文档统一

### 3. 主网准备

- 确认主网真实 DEX / OFT / route
- 主网只读仿真
- 小额真实试运行

### 4. 风控

- 价格偏离保护
- 流动性不足保护
- 重复卖出保护
- 到账未确认保护
